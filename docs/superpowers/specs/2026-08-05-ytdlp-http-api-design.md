# HTTP-ручка для скачивания видео (для Apple Shortcuts)

Дата: 2026-08-05
Статус: согласован, готов к плану реализации

## Задача

Сейчас единственный способ скачать видео — написать боту в Telegram, забрать файл из
чата и сохранить его в Фото. Хочется убрать Telegram из этой цепочки: поделиться
ссылкой из TikTok/Reels/Shorts через Share Sheet, и чтобы видео сразу оказалось в
Фотоплёнке.

Для этого сервису нужна HTTP-ручка: принимает URL, возвращает готовый mp4. Шорткат на
iPhone дёргает её и кладёт ответ в Фото.

Сценарий ограничен короткими видео (до ~3 минут). Длинные YouTube-ролики через эту
ручку не качаем — это меняло бы дизайн на асинхронный с job'ами и polling'ом.

## Решение

Синхронная ручка на существующем HTTP-сервере сервиса (том же, где `/metrics`):
запрос приходит, внутри выполняется знакомый пайплайн `yt-dlp → ffmpeg`, файл уходит
в теле ответа. Ни очередей, ни хранилища, ни состояния.

Почему в текущем сервисе, а не отдельным бинарём: логика скачивания уже живёт в
`video_manager`, в образе есть ffmpeg, CI и деплой настроены. Отдельный контейнер дал
бы изоляцию по ресурсам и рестартам, но на личном сервере эта изоляция не окупает
второй порт, второй vhost в прокси и второй сервис в compose. Паника в HTTP-хэндлере
не роняет процесс — `net/http` её перехватывает, так что бот от соседства не
страдает.

## Контракт API

```
POST /api/download
Authorization: Bearer <API_TOKEN>
Content-Type: application/json

{"url": "https://www.tiktok.com/@user/video/123"}
```

Успешный ответ — `200` с телом-файлом:

```
Content-Type: video/mp4
Content-Disposition: attachment; filename="TikTok - Something.mp4"
Content-Length: <размер>
```

Названия роликов часто содержат кириллицу и эмодзи, поэтому имя файла отдаётся в двух
формах: ASCII-транслитерация в `filename=` и процентное кодирование в `filename*`
(RFC 5987).

Ошибки — JSON `{"error": "..."}`:

| Код | Когда |
|---|---|
| 400 | тело не парсится, URL пустой, схема не `https`, хост — IP-литерал или приватный адрес |
| 401 | нет заголовка `Authorization` или токен не совпал |
| 413 | видео превысило лимит по размеру или длительности |
| 429 | все слоты параллельных загрузок заняты |
| 502 | yt-dlp или ffmpeg завершились с ошибкой |
| 504 | не уложились в дедлайн запроса |

`413` от `502` отличаем по выводу yt-dlp: при срабатывании `--max-filesize` и
`--match-filter` он не скачивает файл и печатает об этом в лог, код возврата при этом
не отличается от прочих отказов. Значит, маппинг идёт по строке вывода, и если
разобрать её не удалось — отдаём `502`.

POST с JSON вместо `GET /api/download?url=...`, потому что query-строка попадает в
логи прокси и в историю запросов. В Shortcuts разницы нет: «Get Contents of URL»
умеет JSON-body одним полем.

## Авторизация

Статический токен в переменной `API_TOKEN`, заголовок `Authorization: Bearer <token>`,
сравнение через `subtle.ConstantTimeCompare` — как уже сделано для basic auth на
`/metrics` в `cmd/service/main.go`.

Если `API_TOKEN` пуст, роут не регистрируется, в лог уходит WARN. Так выкатка без
нового env не роняет бота — в отличие от `METRICS_USERNAME`/`METRICS_PASSWORD`,
где пустое значение приводит к `Fatal`.

Ручка смотрит в интернет через домен с HTTPS, так что токен не ходит открытым
текстом.

## Пайплайн обработки

1. Проверить токен.
2. Занять слот в семафоре (`maxConcurrent = 2`), иначе сразу `429`.
3. Разобрать и провалидировать URL: схема `https`, хост не IP-литерал из приватного
   или loopback-диапазона. Открытая ручка к yt-dlp — это заодно и SSRF-примитив,
   проверка стоит десяти строк. DNS не резолвим: домен, указывающий на `127.0.0.1`,
   такую проверку пройдёт. Полная защита потребовала бы резолва с последующим
   контролем, куда пойдёт сам yt-dlp, — несоразмерно для ручки под личным токеном.
4. Создать временный каталог на запрос (`os.MkdirTemp`), `defer os.RemoveAll`.
5. Скачать в этот каталог с лимитами `--max-filesize 500M` и
   `--match-filter "duration < 900"`.
6. Проверить через `ffprobe`, нужен ли транскод. Если контейнер mp4, видео H.264,
   звук AAC — отдать файл как есть. Reels и TikTok почти всегда приходят такими, а
   транскод 1080p×3мин на слабом VPS занимает десятки секунд, которые пользователь
   ждёт с телефоном в руке.
7. Иначе транскодировать в тот же каталог существующим ffmpeg-пайплайном.
8. Отдать файл в ответ через `io.Copy`.

Временный каталог на запрос попутно чинит существующую гонку: сейчас все загрузки
пишут в рабочую директорию по шаблону `%(extractor)s - %(title)s.%(ext)s`
(`internal/services/video_manager/service.go`), и два одинаковых URL одновременно
спотыкаются о `NoOverwrites`. Бот уже держит до 5 параллельных загрузок
(`maxConcurrent` в `internal/services/message_handler/handler.go`), так что гонка
возможна и без API.

## Изменения в коде

`internal/services/video_manager/service.go`
- `DownloadVideoTo(ctx, url, dir) (string, error)` — строит свой `*ytdlp.Command` на
  каждый вызов вместо общего поля структуры, пишет в переданный каталог, принимает
  контекст снаружи. Константа `downloadTimeout = 10 * time.Minute` уезжает из
  `video_manager` к вызывающим: бот заводит свой контекст с прежними 10 минутами, API
  — с дедлайном запроса в 5 минут.
- `TranscodeVideoTo(ctx, inputPath, dir) (string, error)` — то же для транскода.
- `NeedsTranscode(path) (bool, error)` — `ffprobe` на контейнер и кодеки.
- Бот переводится на новые методы, старые убираются. Это не отдельный рефакторинг:
  ручка и бот делят один `video_manager`, и оставлять в нём два способа скачивания
  ради обратной совместимости не с кем.

`internal/handlers/api/download.go` (новый пакет)
- middleware проверки токена;
- разбор и валидация тела запроса;
- вызов `video_manager`, маппинг ошибок в коды из таблицы выше;
- запись файла в `ResponseWriter` с заголовками.

`cmd/service/main.go`
- регистрация роута на существующем mux;
- семафор параллельных загрузок;
- `ReadHeaderTimeout` на сервере. `WriteTimeout` не ставим — он оборвёт отдачу
  большого файла; вместо него дедлайн 5 минут на контексте запроса.

`internal/infrastructure/metrics/metrics.go`
- счётчик `api_requests_total{status}`. Длительности скачивания и транскода уже
  пишутся внутри `video_manager`.

`Dockerfile` — правок, скорее всего, не нужно: `ffprobe` приходит вместе с пакетом
`ffmpeg`. Проверяется при реализации.

`.env.example`, `README.md`, `CLAUDE.md` — новая переменная и описание ручки.

## Тесты

Тестов в проекте нет, поэтому набор минимальный и покрывает единственное место с
нетривиальной логикой — HTTP-хэндлер. `VideoManager` уже интерфейс, так что фейк
подставляется без сети и ffmpeg.

Table-driven тесты на:
- авторизацию: нет заголовка, кривой формат, неверный токен, верный токен;
- валидацию URL: http вместо https, IP-литерал, приватный адрес, пустое тело,
  битый JSON;
- маппинг ошибок `video_manager` в коды ответа;
- успешный путь: заголовки `Content-Type`, `Content-Disposition` и тело.

Проверять реальное скачивание с ютуба тестами не будем — это тест на внешний мир.

## Шорткат на iPhone

1. `Get Contents of URL` — `https://<домен>/api/download`, метод POST, заголовок
   `Authorization: Bearer <токен>`, Request Body: JSON, поле `url` = Shortcut Input.
2. `Save to Photo Album`.
3. В настройках шортката включить Show in Share Sheet, тип входа — URLs.

Пошаговая инструкция со скриншотами-описаниями идёт в README.

## Чего осознанно не делаем

- Асинхронные job'ы с polling'ом — сценарий ограничен короткими видео.
- Хранение скачанных файлов и раздачу по ссылкам — файл живёт только в теле ответа.
- Историю загрузок, БД, кеш по URL — сервис остаётся stateless.
- Ротацию токенов и несколько пользователей — инструмент личный.
- Выбор качества и формата параметрами запроса — до появления реальной нужды.

## Риски

Ручка и бот делят процесс и CPU: параллельные транскоды замедлят и то и другое.
Семафор на 2 запроса ограничивает ущерб, но при регулярных жалобах на скорость
правильный следующий шаг — вынести API в отдельный контейнер (вариант B из
обсуждения), а не наращивать лимиты.

Токен статический и не ротируется. Утечка означает открытый yt-dlp наружу с
ресурсами сервера; смена токена — это правка env и рестарт.
